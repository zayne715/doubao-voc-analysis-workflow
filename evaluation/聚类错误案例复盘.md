# Issue Clustering Bad Cases

## 文档目的

本文档记录 Issue Clustering 阶段发现的典型 Bad Case，
包括：

- 实际聚类结果
- 人工判断的合理结果
- 错误类型
- 原因分析
- 优化方案
- 优化后的真实结果

用于支持：

Issue Clustering Prompt 迭代
→ 聚类结果复核
→ Error Analysis
→ 项目复盘

---

# IC-BC-001｜相同回答错误因表达差异被拆分

## 当前版本

Issue Clustering V2

## Actual

当前被拆分为多个 Cluster，例如：

- AI回答内容错误不准确
- AI回答偶发差错异常

## Expected

更合理的聚类方式：

AI回答内容错误 / 不准确

## Error Type

Over-segmentation

聚类过细。

## 问题分析

这些反馈描述的核心产品问题都是：

AI 输出的回答存在错误或不准确。

“偶发”“经常”“有点错误”等差异，
本质上属于：

- 发生频率差异
- 严重程度差异
- 用户表达强度差异

不应该因此形成不同产品 Issue。

如果拆得过细，
会导致同一个问题的 Frequency 被分散，
从而影响后续 Priority Score。

## 优化方向

增加规则：

同一核心产品问题，
不得仅因为以下差异拆成不同 Cluster：

- 发生频率
- 严重程度
- 情绪强度
- 用户措辞

例如：

“偶尔回答错误”
“回答经常出错”
“答案不准确”

应优先归入：

AI回答内容错误 / 不准确

## Status

Pending V3

# IC-BC-002｜回答质量问题被拆得过细

## 当前版本

Issue Clustering V2

## Actual

当前存在多个较细 Cluster，例如：

- 回答空泛缺乏实质内容
- AI回答内容冗长废话多

## Expected

可以考虑合并为：

回答空泛冗余、信息密度低

## Error Type

Over-segmentation

## 问题分析

“内容空泛”和“废话较多”虽然表达不同，
但用户感受到的核心问题非常接近：

回答产生了大量内容，
但有效信息不足。

从产品分析角度看，
两者通常会进入同一个问题卡片进行进一步验证。

## 优化方向

聚类时不仅比较表面关键词，
还应比较：

用户最终感知的问题
+
可能需要采取的产品改善方向

如果两个反馈的核心用户痛点和改善方向高度一致，
应优先合并。

## Status

Pending V3

# IC-BC-003｜对话风格问题被拆得过细

## 当前版本

Issue Clustering V2

## Actual

存在：

- 回复风格机械、人机感强
- AI回答表现出反驳性人格
- 安慰性回复被感知为嘲讽

## Expected

可进一步评估是否合并为：

对话语气 / 风格体验不自然

或者根据最终数据量保留必要子类。

## Error Type

Possible Over-segmentation

## 问题分析

这些问题都不属于：

回答事实正确性

而更接近：

AI表达方式、语气、人格感和交流体验。

当前样本量较小时，
过细拆分容易产生大量 Singleton Cluster。

但需要注意：

如果未来数据扩大后，
某一种具体风格问题出现大量反馈，
仍可以重新拆成独立 Issue。

## 优化方向

聚类粒度应结合数据规模：

小样本 MVP 阶段：
优先形成具有统计意义的稳定问题簇。

大样本阶段：
若某类问题形成明显独立反馈规模，
再细分子 Issue。

## Status

Pending V3

# IC-BC-004｜自动新话题问题被按不同表象拆分

## 当前版本

Issue Clustering V2

## Actual

当前被拆为：

- 对话自动切换新话题
- 对话自动刷新导致上下文丢失
- 查找聊天记录未提示对话分开原因

## Expected

更合理的核心产品问题：

对话自动分段 / 切换导致上下文中断

## Error Type

Symptom Fragmentation

同一核心产品事件被按照不同表现拆分。

## 问题分析

这些反馈分别描述：

触发行为：

- 自动开启新话题
- 自动刷新

直接结果：

- 上下文丢失
- AI失忆

用户可见表现：

- 聊天记录没有说明为什么被分开

虽然表面现象不同，
但它们都围绕同一个核心产品事件：

系统自动改变对话边界，
导致对话连续性中断。

当前还存在一个架构问题：

第一层聚类使用：

Category + Feature

作为预分组边界。

因此不同 Category / Feature 的相关 Issue
根本不会进入同一次 LLM 聚类。

## 优化方向

V3 增加：

核心产品事件优先原则。

同时增加第二阶段：

Global Cluster Consolidation

允许跨 Category / Feature 检查：

是否实际上属于同一个产品问题。

## Status

Pending V3 + Consolidation V1

# IC-BC-005｜桌面入口问题因表达方式和 Category 不同被拆分

## Actual

- 安装后桌面未显示应用图标
- 希望支持添加豆包到桌面

## Expected

桌面应用入口缺失或无法添加

## Error Type

Problem-Solution Fragmentation

Cross-category Fragmentation

## 问题分析

第一条使用“问题”表达：

安装后没有桌面入口。

第二条使用“解决方案需求”表达：

希望支持添加到桌面。

但两者背后的用户目标一致：

希望能够从桌面直接进入豆包。

由于两条 Issue Category 不同，
当前 Category + Feature 预分组无法将其合并。

## 优化方向

增加规则：

如果一条反馈描述产品问题，
另一条反馈提出解决该问题的功能方案，

且底层用户需求相同，

则最终 Cluster 应优先按照共同问题聚合，
而不是因为“问题 / 功能需求”的表达形式不同而拆分。

## Status

Pending Consolidation V1

---

# IC-BC-006｜产品臃肿问题与极速版需求被拆分

## Actual

- 功能过多且存在冗余功能
- 希望推出精简功能极速版

## Expected

功能过多导致产品臃肿

## Error Type

Problem-Solution Fragmentation

## 问题分析

“希望推出极速版”实际上是用户针对：

产品功能越来越多、使用体验变复杂

提出的一种解决方案。

真正应该被统计的用户问题是：

产品过于臃肿，希望更加精简。

如果直接使用：

“希望推出极速版”

作为 Cluster Name，

容易把用户提出的具体方案错误地当作底层产品问题。

## 优化方向

Cluster Name 优先描述：

用户问题 / 用户痛点

而不是直接采用用户提出的具体解决方案。

例如：

不推荐：

希望推出极速版

推荐：

功能过多导致产品臃肿

## Status

Pending Consolidation V1

---

# IC-BC-007｜学习搜题错误被拆成多个相近 Issue

## Actual

当前存在：

- AI解答题目结果错误
- 作业检查结果错误
- 题目数量识别错误

## Expected

其中：

AI解答题目结果错误
+
作业检查结果错误

可以考虑合并为：

学习 / 搜题结果错误

但是：

题目数量识别错误

暂时不直接合并。

## Error Type

Mixed Granularity

## 问题分析

“解答错误”和“作业检查错误”
核心问题都发生在：

最终答案 / 判断结果的正确性。

而：

“六道题识别成五道题”

属于输入或题目识别阶段的问题。

两者可能需要不同的产品验证方法：

识别问题：
关注题目检测、输入理解。

解答问题：
关注推理和答案正确性。

因此不能因为都属于“搜题”
就全部合成一个大 Cluster。

## 优化方向

聚类时区分：

输入识别问题
≠
理解问题
≠
最终回答 / 解答结果问题

避免过度合并。

## Status

Pending V3

# 一、整体问题分析

本轮 V2 聚类主要暴露出三类问题。

## 1. Over-segmentation

同一产品问题因为：

- 表达方式不同
- 频率不同
- 严重程度不同
- 用户措辞不同

被拆成多个 Cluster。

结果：

同一问题 Frequency 被稀释。

---

## 2. Symptom Fragmentation

同一个核心产品事件的：

- 触发行为
- 中间表现
- 后续结果
- UI表现

被分别建立 Cluster。

典型案例：

自动开启新话题
→ 上下文中断
→ 聊天记录未解释分段原因

---

## 3. Cross-category Fragmentation

当前第一阶段使用：

Category + Feature

作为聚类预分组。

优点：

降低 Token 消耗，
避免完全不相关问题被错误合并。

缺点：

同一个产品问题如果被表达成：

- AI效果问题
- 交互体验
- 功能需求

则无法在第一阶段被合并。

因此单纯修改第一层 Prompt
无法完全解决当前问题。

---

# 二、计划修改方案

本轮采用两级聚类结构。

## Stage 1｜Issue Clustering V3

继续在：

Category + Feature

组内进行语义聚类。

主要解决：

- 聚类过细
- Cluster Name 太泛
- 因频率 / 强度差异错误拆分
- Problem 与 Solution 表达差异
- 聚类粒度不稳定

---

## Stage 2｜Global Cluster Consolidation V1

输入第一阶段产生的 Cluster。

在全局范围再次判断：

是否存在多个 Cluster
实际描述同一个核心产品问题。

允许跨：

- Category
- Feature

进行合并。

但 Category / Feature 仍作为重要参考信息，
不能无条件跨模块合并。

重点解决：

- Cross-category Fragmentation
- Problem-Solution Fragmentation
- 同一核心产品事件被不同表象拆分

---

# 三、V3 重点规则

计划新增以下核心规则：

1. 同一核心问题不得仅因发生频率不同而拆分。

2. 同一核心问题不得仅因严重度不同而拆分。

3. “描述问题”和“提出解决该问题的需求”
   如果底层用户痛点一致，
   应优先视作同一个产品问题。

4. 判断是否应该合并时，
   优先判断：
   “产品经理是否会把这些反馈放在同一张问题卡片中，
   并用基本相同的产品动作进行验证或改善？”

5. Cluster Name 必须描述具体、可观察的问题。

禁止过度泛化名称，例如：

- AI能力不足

- AI不好用

- 使用体验差

- 功能异常

- AI回答有问题
6. 同时防止过度合并。

例如：

- 理解错误 ≠ 事实错误
- 指令遵循失败 ≠ 回答错误
- 内容偏见 / 安全问题 ≠ 普通回答质量问题
- 输入识别错误 ≠ 最终解答错误
- UI入口问题 ≠ 实际功能自动触发问题

# 五、最终结论

Pending

最终不只判断：

“Cluster 数量有没有减少”。

还需要判断：

1. 同一问题是否真正被聚合；
2. 不同问题是否被错误合并；
3. Cluster Name 是否稳定、可解释；
4. Frequency 是否更接近真实用户问题分布；
5. 聚类结果是否适合进入 Priority Score。
