# 豆包用户反馈智能分析工作流

## 1. 项目定位

本项目是一套面向产品经理的公开用户反馈（VOC）分析工作流。系统从应用宝获取豆包公开评论，使用 n8n 编排数据处理流程，调用大语言模型完成质量筛选、问题拆分、语义聚类和产品洞察生成，再通过可解释的规则计算问题优先级，最后交给产品经理审核。

项目遵循以下协作边界：

- AI 负责自然语言理解、结构化抽取、语义归纳和洞察草拟。
- 确定性规则负责数据清洗、统计、Priority Score 和结果校验。
- 产品经理负责审核、修改、驳回和最终产品决策。

系统输出只代表公开样本中的用户信号，不代表豆包全部用户，也不用于推断内部技术根因或业务指标。

## 2. 当前能力

当前代码已经形成从采集到人工审核的完整纵向链路：

```text
启动分析
  -> 采集应用宝公开评论
  -> 标准化、去空、按评论 ID 去重和数量截断
  -> 评论质量筛选
  -> Feedback Analyzer 拆分结构化 Issue
  -> 按 Category + Feature 进行第一阶段聚类
  -> 全局 Cluster Consolidation
  -> Issue Statistics
  -> Priority Score
  -> 问题类 / 正向 Product Insight
  -> 正向整体报告
  -> PM Review 入库
  -> Dashboard 展示与人工审核
```

配套能力包括：

- 独立的分析启动、状态查询和错误处理工作流。
- 支持 8 个缓存阶段的 DeepSeek 校验缓存代理；正向整体报告阶段 `positive-overall` 直通、不缓存。
- 按分析批次隔离结果，避免不同批次数据混用。
- 模型输出格式与业务字段校验，校验失败时停止后续写入。
- 前端批次发现、状态轮询、失败阶段展示和 PM Review。

## 3. 数据来源与输入约束

当前仅支持应用宝公开评论，目标应用包名为 `com.larus.nova`。

启动分析时：

- `source` 必须为 `应用宝`。
- `limit` 必须是 10–1000 之间的整数。
- 采集按每页 10 条生成分页请求。
- 评论时间统一转换为 `Asia/Shanghai` 时间。
- 使用应用宝评论 ID 去重，不按评论文本去重。
- 空评论会被丢弃，最终结果按请求数量截断。

标准化字段为：

- `source_comment_id`
- `content`
- `rating`
- `review_date`
- `source`
- `app_version`

## 4. AI 分析与聚类

### 4.1 评论质量筛选

Quality Filter 只判断评论是否包含可用于产品分析的具体信息。它不负责 Category、Feature 或 Severity 分类。

筛选结果必须同时满足：

- `parse_status = success`
- `is_valid` 是布尔值

如果质量筛选没有返回合格结构，工作流直接失败；如果整批评论都无效，则批次以“没有可分析的有效评论”正常结束，不进入后续模型阶段。

### 4.2 Feedback Analyzer

有效评论由 Feedback Analyzer V2 拆分为一个或多个独立 Issue。主要字段包括 Category、Feature、Sentiment、Severity、User Need、Summary 和 Confidence。

标签和拆分边界以[标签体系设计](./标签体系设计.md)为准。不得因为评论出现在豆包页面就把外部产品问题归因给豆包，也不得无证据推断内部技术原因。

### 4.3 两阶段聚类

第一阶段先按 `Category + Feature` 分组，再在组内进行语义聚类；第二阶段对第一阶段 Cluster 做全局合并，用于消除跨 Category、跨 Feature 或“问题描述与解决方案需求”形成的真实重复。

聚类目标是消除真正重复的问题，同时保留产品环节、问题机制或用户影响上的必要差异，而不是机械压缩 Cluster 数量。

## 5. Priority Score

纯正向 Cluster 不参加问题优先级计算，标记为 `excluded`。

其余 Cluster 使用 Priority v1：

```text
Frequency Score = feedback_count / 本批次最大 feedback_count * 100
Severity Score  = (avg_severity - 1) / 4 * 100
Sentiment Score = (negative_rate + neutral_rate * 0.5) * 100

Priority Score  = Frequency Score * 40%
                + Severity Score  * 40%
                + Sentiment Score * 20%
```

Priority Level：

- High：`score >= 65`
- Medium：`45 <= score < 65`
- Low：`score < 45`
- Excluded：纯正向 Cluster

排序依次比较 Priority Score、Feedback Count、Avg Severity、Negative Rate 和 Final Cluster ID。系统会再次独立校验公式、分数范围、等级、排名连续性和正向排除规则；验证失败时停止 Product Insight 和数据写入。

## 6. Product Insight 与人工审核

问题类 Cluster 与正向 Cluster 使用不同的 Product Insight 路径。问题类洞察支持一次补充重试，所有洞察必须通过结构与内容校验后才能写入审核数据。

PM Review 使用 `analysis_run_id + final_cluster_id` 生成唯一 `review_key`，保证不同分析批次相互隔离。

问题类洞察支持以下状态：

- `pending`
- `approved`
- `modified`
- `rejected`

正向洞察无需逐条审批，状态为 `not_required`。AI 原始内容与 PM 修改内容分字段保存，人工修改不会覆盖原始 AI 输出。

## 7. 批次、状态与异常处理

每次请求生成唯一的 `analysis_run_id`。启动接口返回“请求已接收”只代表参数校验通过并尝试启动工作流，不代表分析完成。

分析运行状态单独保存并通过状态 API 查询。前端每 10 秒轮询一次；状态 API 用于解释运行中、失败、无有效评论等状态，而 PM 洞察是否可展示仍以该批次成功写入且存在 `batch_write_complete = true` 为准。

错误工作流会将模型格式错误、质量筛选异常、网络或模型服务异常等技术错误转换为产品经理可理解的提示。原始异常保留在 n8n 执行记录中，不直接暴露到前端。

如果存在正向洞察但正向整体报告尚未生成，前端每 10 秒查询一次，最长等待 30 分钟；如果批次正常完成且没有正向反馈，则展示明确的空状态说明。

## 8. DeepSeek 缓存

`ai-cache-proxy` 负责当前提速测试版以下 8 个阶段的缓存与响应校验：

1. `quality`（旧版单条阶段兼容保留）
2. `quality-batch`
3. `issue`（旧版单条阶段兼容保留）
4. `issue-batch`
5. `clustering`
6. `global-consolidation`
7. `problem-insight`
8. `positive-insight`

`positive-overall` 正向整体报告阶段绕过缓存读取、缓存写入和代理层专属报告校验；该阶段的响应由 n8n 的报告解析与校验节点处理。

缓存 Key 包含 Namespace、Stage、完整请求 Body，以及启用时的阶段缓存版本。其他缓存阶段只保存成功且通过对应校验的响应。

可通过 `CACHE_VERSION_<STAGE>` 只失效某个阶段的旧缓存，而不影响其他阶段；健康检查会返回支持的 Stage、缓存版本和绕过缓存的 Stage。

## 9. 前端

前端是无构建步骤的原生 HTML、CSS 和 JavaScript 页面，默认连接：

```text
http://localhost:5678/webhook
```

当前 `frontend/`调用提速测试版 Webhook 路径；启动请求使用 `URLSearchParams`，避免 `application/json` 触发跨域 OPTIONS 预检。

主要页面和操作包括：

- Dashboard：批次概览、问题优先级、审核进度和正向摘要。
- 问题洞察：搜索、筛选、排序、详情和人工审核。
- 正向洞察：正向 Cluster 与整体正向报告。
- 开始分析：选择应用宝并输入 10–1000 条评论。
- 批次切换：从服务端查询仍然存在的真实批次，不依赖硬编码历史批次。

## 11. 验证边界

仓库中的工作流、前端和缓存代码能够说明系统设计与已实现能力，但不自动证明当前部署环境可用。端到端验收仍需分别确认：

- n8n 工作流已导入、发布并绑定正确的 Data Table。
- 缓存代理健康检查通过，DeepSeek 凭据和网络可用。
- 应用宝采集接口仍可访问并返回预期结构。
- 状态、错误和主工作流之间的 Workflow ID 配置正确。
- 前端能访问本机 n8n Webhook，并完成一次真实批次的启动、轮询、入库和审核。

本项目不包含 RAG、复杂 Multi-Agent、自动生成 PRD、AI 自动做最终产品决策，也不分析豆包内部 Session、留存率、付费率等非公开数据。
