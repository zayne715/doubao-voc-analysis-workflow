# 前端启动分析故障修复说明

## 1. 已确认的浏览器错误

本次 Network 截图显示：

- Request URL：`http://localhost:5678/webhook/start-analysis`
- Request Method：`OPTIONS`
- Status Code：`500 Internal Server Error`
- Origin：`http://localhost:5500`
- `Access-Control-Request-Headers` 包含 `content-type`

这说明浏览器在正式 POST 前发起的 CORS 预检失败。原前端使用 `Content-Type: application/json`，跨域请求会触发 OPTIONS 预检。

## 2. 同时存在的接口路径不一致

当前提速测试版 Control API 注册的启动路径是：

```text
/webhook/start-analysis-speed-test
```

但截图中的浏览器请求路径是：

```text
/webhook/start-analysis
```

这说明浏览器当时加载的是旧版 `frontend/app.js`，它调用的不是当前提速测试版启动接口。当前项目的 `frontend/` 已改为调用批量版路径：

- `start-analysis-speed-test`
- `555a4d0e-5bc8-4f27-83b8-6b5f06b68a0a-speed-test`
- `5f046625-633b-43e9-9fd8-44b029a7b3a5-speed-test`
- `701829b4-73fd-4d10-aa1d-1a28c170051d-speed-test`

## 3. 修复方式

### 3.1 启动请求改为表单编码

前端使用 `URLSearchParams` 发送 `source` 和 `limit`，浏览器会使用 `application/x-www-form-urlencoded`。这是 CORS safelisted Content-Type，不会仅因 Content-Type 而触发 OPTIONS 预检。

n8n Webhook 会将表单字段解析到 `$json.body`，现有参数校验逻辑可继续读取：

- `body.source`
- `body.limit`

### 3.2 Webhook 限定允许的前端来源

启动 API 与状态 API 的 Webhook 节点配置：

```text
Allowed Origins (CORS):
http://localhost:5500,http://127.0.0.1:5500
```

如果静态前端改用其他端口或域名，必须把实际页面 Origin 加入该列表。Origin 包含协议、主机和端口，不包含路径。

### 3.3 启动顺序

Control API 的执行顺序调整为：

```text
Webhook
  -> Validate Request
  -> IF Request Valid
  -> Upsert Request Status
  -> Execute Dynamic Analysis（Wait for Subworkflow 关闭）
  -> Respond Start Analysis
```

这样只有在 n8n 已尝试成功派发主工作流后，才返回 `request_received`。主工作流仍然异步执行，不等待整批分析结束。

### 3.4 空查询结果

为以下 Data Table Get 节点开启 `Always Output Data`，保证查询无记录时，下游 Code 节点仍能生成空状态响应：

- Analysis Status API：`Data Table - Get Analysis Run Status`
- 主工作流：`Data Table - Get PM Review Items`
- 主工作流：`Data Table - Get Positive Overall Reports`
- 主工作流：`Data Table - Get Positive Insights`

## 4. 导入与发布顺序

1. 备份 n8n 当前三个工作流。
2. 导入并发布 `Doubao - Dynamic Analysis Test .json`。
3. 导入并发布 `Doubao - Analysis Status API.json`。
4. 导入并发布 `Doubao - Analysis Control API .json`。
5. 在 Control API 的 `Execute - Dynamic Analysis` 节点确认 Workflow ID 指向当前提速版主工作流。当前仓库导出的主工作流 ID 为 `HFagstyxhaNF4GBM`，Control API 已指向该 ID。
6. 用 Live Server 从 `frontend/` 启动页面，默认端口 `5500`。不要直接双击 `index.html` 使用 `file://`。

## 5. 验收方法

打开 Chrome DevTools -> Network，清空记录后只提交一次 10 条评论的测试请求。

预期结果：

- 请求 URL 为 `http://localhost:5678/webhook/start-analysis-speed-test`。
- 不应再出现对应的 OPTIONS 预检请求。
- 应出现 POST，状态码为 200。
- Response 应包含 `success: true`、`status: "request_received"` 和有效的 `analysis_run_id`。
- n8n 中应出现 Control API Execution 和对应的主工作流 Execution。
- 状态 API 应能返回 `running`，之后进入 `completed` 或 `failed`。

如果 POST 仍然是 500，请查看 n8n 的 Control API Execution，重点检查 `Execute - Dynamic Analysis` 节点；此时已经不是原来的 OPTIONS 预检问题。
