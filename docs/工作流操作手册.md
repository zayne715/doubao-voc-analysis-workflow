# 豆包用户反馈智能分析工作流 SOP

> 依据当前提速测试版 n8n 工作流、缓存代理和前端代码整理  
> 文档校订日期：2026-11-02
> 用途：本地部署、执行、观察、排错和 PM Review

## 1. 系统组成

| 组件 | 作用 |
| --- | --- |
| Dynamic Analysis Test 提速测试版 | 批量质量筛选、批量 Issue 拆解、聚类、Priority、洞察、入库和 PM Review API |
| Analysis Control API 提速测试版 | 校验启动参数、生成批次编号并触发提速主工作流 |
| Analysis Status API终版 | 按 `analysis_run_id` 返回运行状态 |
| Analysis Error Handler终版 | 捕获主工作流异常并写入面向 PM 的失败原因 |
| ai-cache-proxy | 校验并缓存 8 个阶段；`positive-overall` 直通、不缓存 |
| frontend | 启动分析、轮询状态、展示洞察并提交 PM 审核 |

## 2. 执行前检查

1. 在 n8n 中导入并发布项目根目录中的四个工作流；启动 API 必须指向提速测试版主工作流。
2. 确认主工作流的 Error Workflow 指向错误处理工作流。
3. 确认主工作流、启动 API 和状态 API 使用的 Workflow ID、Data Table ID 与当前 n8n 环境一致。
4. 确认 `ai-cache-proxy` 与 n8n 位于可互通的 Docker 网络，n8n 能访问 `http://ai-cache-proxy:8000`。
5. 为缓存代理配置 `DEEPSEEK_API_KEY`，不要把密钥写进工作流 JSON、前端或仓库。
6. 调用缓存代理 `/health`，确认返回 `status=ok`、支持的 Stage、当前缓存版本，以及 `cache_bypass_stages`。
7. 如果计划启用单评论缓存，设置 `REVIEW_CACHE_ENABLED=1`，并确认 `/health` 中 `review_cache_enabled=true`；首次部署建议保持默认值 `0`。
8. 确认前端能访问 `http://localhost:5678/webhook`。

## 3. 启动分析

当前 `frontend/`已对齐提速版 Webhook 路径。请从项目根目录的 `frontend/` 启动静态页面，不要使用旧版 `/start-analysis` 路径。

前端向以下接口发起 POST 请求：

```text
http://localhost:5678/webhook/start-analysis-speed-test
```

当前前端使用 `application/x-www-form-urlencoded`（`URLSearchParams`）发送 `source` 和 `limit`，避免 `application/json` 触发浏览器 OPTIONS 预检。启动 API 的 Webhook 节点 `Allowed Origins (CORS)` 默认允许 `http://localhost:5500` 与 `http://127.0.0.1:5500`。若 Live Server 使用其他端口，需要同步修改该允许来源。

请求示例：

```json
{
  "source": "应用宝",
  "limit": 100
}
```

参数规则：

- `source` 当前只能是 `应用宝`。
- `limit` 必须是 10–1000 之间的整数。

启动接口会生成：

```text
run_<UTC 时间戳>_<n8n execution id>
```

启动响应只表示请求通过校验并尝试触发主工作流，不表示分析已经完成。保存响应中的 `analysis_run_id`，后续所有状态、结果和审核操作都使用该批次编号。

## 4. 评论采集与标准化

1. 主工作流根据 `limit` 计算页数，每页请求 10 条评论。
2. 从应用宝评论接口读取豆包包名 `com.larus.nova` 的最新评论。
3. 将评论转换为标准字段：评论 ID、正文、评分、北京时间、来源和 App Version。
4. 跳过空评论。
5. 按应用宝评论 ID 去重；相同文本但评论 ID 不同的记录保留。
6. 达到请求数量后停止继续加入结果。当前导出没有独立的数量完整性 Guard；接口返回不足时，应核对实际输出条数。

采集接口或返回结构异常时，主工作流应失败，不得把空结果伪装成成功分析。

## 5. 质量筛选

提速版 Quality Filter 通过缓存代理批量调用 DeepSeek，Stage 为 `quality-batch`；旧版单条 Stage `quality` 保留用于兼容。

每条结果必须满足：

- `parse_status` 为 `success`。
- `is_valid` 是布尔值。

出现空输出、解析失败或字段类型不正确时，Guard 节点终止任务并交给错误工作流处理。

如果全部评论都被正确判定为无效，工作流写入完成状态：

```text
本批次没有可分析的有效评论
```

这属于合法的空业务结果，不属于模型或系统故障。

## 6. Issue 分析与两阶段聚类

### 6.1 Feedback Analyzer

有效评论进入批量 Feedback Analyzer，缓存 Stage 为 `issue-batch`；旧版单条 Stage `issue` 保留用于兼容。一条评论可以拆成多个相互独立的 Issue，输出 Category、Feature、Sentiment、Severity、User Need、Summary 和 Confidence。

### 6.2 第一阶段聚类

先按 `Category + Feature` 分组，再调用 Issue Clustering，缓存 Stage 为 `clustering`。目标是在同一语义范围内合并表达不同但核心问题一致的 Issue。

### 6.3 全局合并

第一阶段 Cluster 再进入 Global Cluster Consolidation V1，缓存 Stage 为 `global-consolidation`。该阶段允许跨 Category、跨 Feature 合并真正重复的问题，但禁止为减少数量强行合并。

### 6.4 统计

Issue Statistics 计算 Feedback Count、Issue Count、Feedback Share、Severity 和 Sentiment 等指标。Merge 节点使用 Append 汇总 Final Cluster 与原始 Issue，不是字段 Join。

## 7. Priority Score v1

纯正向 Cluster 不参加问题优先级，标记为 `excluded`。

问题型 Cluster 的分数为：

```text
Frequency Score = feedback_count / max_feedback_count * 100
Severity Score  = (avg_severity - 1) / 4 * 100
Sentiment Score = (negative_rate + neutral_rate * 0.5) * 100

Priority Score  = Frequency Score * 0.40
                + Severity Score  * 0.40
                + Sentiment Score * 0.20
```

等级规则：

| 等级 | 条件 |
| --- | --- |
| High | `score >= 65` |
| Medium | `45 <= score < 65` |
| Low | `score < 45` |
| Excluded | 纯正向 Cluster |

同分时依次比较 Feedback Count、Avg Severity、Negative Rate 和 Final Cluster ID。

Validate Priority Results 会重新计算并检查：公式版本、参与资格、分数组成、0–100 范围、等级、排名连续性和正向排除字段。任何检查失败都必须阻止后续洞察生成和入库。

## 8. Product Insight

### 8.1 问题类洞察

问题 Cluster 使用 `problem-insight` Stage。第一次结果解析失败时可进入一次 Retry，Retry 必须仍然对应原 Final Cluster ID，禁止错误复用其他 Cluster 的缓存结果。

### 8.2 正向洞察

纯正向 Cluster 使用 `positive-insight` Stage，不生成问题 Priority。正向洞察入库后，再使用 `positive-overall` Stage生成本批次整体正向报告。

如果批次没有正向洞察，不应伪造整体正向报告；应保存并展示“没有正向反馈”的业务说明。

### 8.3 写入门禁

所有 Product Insight 必须整批通过校验，才能准备数据输出。校验失败时停止写入，避免前端读取到部分成功、部分损坏的批次。

## 9. PM Review 入库与完成标记

每条审核记录使用以下唯一键：

```text
review_key = analysis_run_id + "__" + final_cluster_id
```

写入前检查：

- 同一批次内 `review_key` 不重复。
- 所有记录的 `analysis_run_id` 相同。
- 问题洞察初始状态为 `pending`。
- 正向洞察状态为 `not_required`。
- 只写入允许字段，不把中间调试字段带入审核表。

全部记录写入成功后，只在最后一条记录上设置：

```text
batch_write_complete = true
```

前端只有在查到批次数据且该标记为真时，才把本批次视为可展示的完整结果。

## 10. 前端状态与轮询

- 分析状态每 10 秒查询一次。
- 状态 API 是辅助判断；洞察完整性以 `batch_write_complete` 为准。
- 前端从 PM Review API 获取当前真实存在的批次，不使用硬编码历史批次。
- 失败时展示失败阶段和归一化原因。
- 接口返回空 Body 或非 JSON 时，前端显示明确错误，不继续当成正常数据处理。
- 存在正向洞察但整体报告尚未完成时，每 10 秒查询一次，最长等待 30 分钟。

状态接口可能返回：

| 状态 | 含义 |
| --- | --- |
| `running` | 主分析仍在执行 |
| `completed` | 主工作流已经写入完成状态 |
| `failed` | 错误工作流记录了失败 |
| `not_found` | 尚未查到该批次状态；不能单独视为终态 |
| `invalid_request` | `analysis_run_id` 缺失或格式错误 |

## 11. PM 人工审核

问题洞察支持：

- 通过：`approved`
- 保存修改：`modified`
- 驳回：`rejected`

PM 修改内容写入独立字段，AI 原始洞察必须保留。审核请求必须携带正确的批次号和 `review_key`，前端不得把其他批次的数据提交到当前批次。

正向洞察用于展示用户认可的能力和体验，不要求逐条审批。

## 12. 缓存运行规则

缓存代理识别以下 Stage：

```text
quality
quality-batch
issue
issue-batch
clustering
global-consolidation
problem-insight
positive-insight
positive-overall
```

其中除 `positive-overall` 外的 8 个 Stage 使用缓存；`positive-overall` 只作为请求标记，实际绕过缓存读取、缓存写入和代理层专属报告校验，响应直接交给 n8n 的 `Parse & Validate Positive Overall Report` 节点处理。

其他 8 个 Stage 的缓存 Key 包含 Namespace、Stage、完整请求 Body 和可选的阶段版本。只有 HTTP 200、正常结束、JSON 合法且通过对应阶段业务校验的响应才会写入缓存。失败、超时、字段不完整、Cluster ID 不匹配或校验失败的响应不会缓存。

修改某阶段 Prompt、解析契约或业务语义后，可更新对应的 `CACHE_VERSION_<STAGE>`。例如：

```text
CACHE_VERSION_ISSUE=v2
```

只会影响 Issue 阶段的缓存 Key，不影响其他阶段。

## 13. 错误处理

错误工作流根据执行 ID 查找对应批次，并只在主分析仍处于运行状态时写入失败，避免晚到的错误覆盖已完成结果。

面向 PM 的失败原因分为：

- 质量筛选没有有效输出。
- 模型返回格式或字段校验失败。
- 模型服务限流、额度、超时或网络异常。
- 指定节点发生其他未分类中断。

原始技术错误保留在 n8n Executions 中。前端只展示经过归一化、可操作的说明。

## 14. 验收清单

一次完整验收至少检查：

1. 启动接口拒绝非应用宝来源和范围外数量。
2. 合法请求返回唯一 `analysis_run_id`，且响应不误称已经完成。
3. 状态记录从运行中进入完成或失败终态。
4. 采集数量不超过请求值，空评论被移除，评论 ID 不重复。
5. 模型各阶段返回结构通过校验，错误响应没有进入缓存。
6. Priority 公式为 40% / 40% / 20%，纯正向 Cluster 被排除。
7. 问题与正向洞察都绑定当前批次。
8. PM Review 数据全部写入后才出现 `batch_write_complete = true`。
9. 前端不会展示其他批次数据，能够显示失败阶段和空业务结果。
10. PM 修改不覆盖 AI 原始洞察。

## 15. 已知边界

- 当前只支持应用宝公开评论。
- 外部采集接口结构可能变化，需要真实运行验证。
- 工作流 JSON 中的 Workflow ID、Data Table ID 和 Webhook 地址与具体 n8n 环境绑定。
- 仓库代码和历史数据不能代替真实 n8n、DeepSeek、Docker 网络与前端联调。
- 系统输出用于辅助产品判断，不自动生成最终产品决策，也不代表豆包全部用户。
