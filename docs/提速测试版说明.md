# 豆包用户反馈分析工作流：批量提速测试版说明

## 1. 这份测试版改了什么

本文件记录批量提速改造与验证方式。**当前项目包只包含已投入使用的批量工作流导出，不包含改造前的旧版 JSON；不应将文中的历史测试部署步骤直接执行到已经正常运行的 n8n 实例。**提速改造只替换前置的两段逐条模型请求：

| 阶段 | 原流程 | 提速测试版 | 每 50 条评论的请求量（全部有效时） |
|---|---|---|---:|
| 质量筛选 | 每条评论一次请求 | 每 3 条评论一次请求 | 50 → 17 |
| Issue 拆解 | 每条有效评论一次请求 | 每 2 条有效评论一次请求 | 最多 50 → 最多 25 |

两阶段仍然分开执行，质量筛选规则、Issue 拆分规则、Category、Feature、Sentiment、Severity、User Need、Summary、Confidence 等业务规则沿用原提示词。后续组内聚类、全局合并、Priority、Problem Insight、Positive Insight 和整体正向报告不做结构性改造。

注意：批量处理会减少请求次数和请求间等待，但单次请求输入/输出更大。10 分钟是验收目标，不是已经实测保证的结果。

## 2. 文件说明

- `Doubao - Dynamic Analysis Test .json`：独立的主分析子工作流，包含批量分组、批量模型请求和按评论 ID 展开结果。
- `Doubao - Analysis Control API .json`：独立的启动 API，已指向提速测试主工作流。
- `frontend/`：当前唯一的前端目录，启动接口保留 `-speed-test` 路径后缀。
- `ai-cache-proxy/app.py`：增加 `quality-batch`、`issue-batch` 两种缓存阶段校验器；旧阶段保留。
- `ai-cache-proxy/tests/test_proxy.py`：新增批量阶段缓存、输出完整性和评论 ID 对应关系测试。

## 3. n8n 导入顺序（仅新环境部署）

1. 先备份当前 n8n 的主分析工作流和 Analysis Control API 工作流。
2. 导入 `Doubao - Dynamic Analysis Test .json`。
3. 导入 `Doubao - Analysis Control API .json`。
4. 检查 Control API 副本中的 `Execute - Dynamic Analysis` 节点，其 Workflow ID 应指向刚导入的提速测试主工作流。若 n8n 导入时自动分配了不同 ID，请在该节点重新选择刚导入的提速测试主工作流。
5. 仅在新环境首次导入时检查节点配置和凭据引用；当前已运行环境不需要重新导入或停用工作流。
6. 当前 Webhook 路径仍保留 `-speed-test` 后缀；这是接口名称，不表示存在另一套旧版工作流。

当前批量版仍然使用项目现有的 Data Tables 和 Error Handler，因此不会自动创建一套独立数据库。测试时建议使用新的分析批次 ID，并避免与正式任务同时写入相同业务表。

## 4. 更新缓存代理（历史部署说明，已运行环境无需执行）

提速测试版会发送新的 `X-Cache-Stage`：

- `quality-batch`
- `issue-batch`

历史旧版代理不认识这两个阶段，新环境部署前需要核对代理镜像版本；**已正常运行的环境不要再次执行下述覆盖和重启命令。**为了避免误删当前容器或丢失卷、网络、环境变量，不要直接删除并重建容器。可以先在 PowerShell 里备份容器中的旧文件，再复制新文件并重启：

```powershell
# 在解压后的项目根目录执行

docker cp ai-cache-proxy:/app/app.py .\app.py.before-speed-test.py

docker cp .\ai-cache-proxy\app.py ai-cache-proxy:/app/app.py

docker restart ai-cache-proxy

docker logs --tail 80 ai-cache-proxy
```

检查代理健康状态：

```powershell
docker exec ai-cache-proxy python -c "import urllib.request; print(urllib.request.urlopen('http://localhost:8000/health').read().decode())"
```

返回的 `stages` 应包含 `quality-batch` 和 `issue-batch`。此方式会在当前容器文件系统中更新代码，容器重建后会恢复镜像内的旧代码；正式部署时再按实际容器启动参数重建镜像。

如果代理启动失败，回滚：

```powershell
docker cp .\app.py.before-speed-test.py ai-cache-proxy:/app/app.py
docker restart ai-cache-proxy
```

## 5. 前端测试

当前 `frontend/index.html` 已对齐批量版接口，直接使用 `frontend/`。启动、PM Review 和 Positive Report Webhook 都带 `-speed-test` 后缀；状态查询仍复用现有 Status API。

启动请求改用 `URLSearchParams`（`application/x-www-form-urlencoded`），避免 `application/json` 触发浏览器 OPTIONS 预检。启动 API 与状态 API 的 Webhook `Allowed Origins (CORS)` 需允许前端 Origin，默认配置为 `http://localhost:5500,http://127.0.0.1:5500`。

## 6. 历史验收和可选性能评估（会调用 API，请谨慎）

### 历史验收用例：10 条评论

- 使用 10 条新评论。
- 确认 Quality Filter 返回数量等于输入评论数。
- 确认每条 `source_comment_id` 对应的 `is_valid` 正确。
- 确认 Analyzer 输出的 Issue 仍然能回到正确的 `source_comment_id`。
- 检查聚类、洞察和报告是否完整。

### 可选性能评估用例：50 条评论（会产生 API 费用）

记录以下时间：

| 记录项 | 需要观察的内容 |
|---|---|
| 总耗时 | 从启动到所有报告入库 |
| Quality Batch | 批次数、平均请求耗时、是否有 429 |
| Analyzer Batch | 批次数、平均请求耗时、是否有 JSON 截断 |
| Clustering / Consolidation | 每个节点执行时间 |
| Product Insight | 实际 Cluster 数量及逐个请求耗时 |
| 缓存 | HIT / MISS 数量及是否出现错误缓存 |

验收标准：50 条评论总耗时不超过 10 分钟；没有漏评论、重复评论、跨评论串数据；聚类和洞察结果质量与原版基本一致。

## 7. 重要边界和回退

- Quality Filter 批次大小为 3；Feedback Analyzer 批次大小为 2。Analyzer 输出更长，暂不设为 3，降低 JSON 截断和跨评论错配风险。
- 代码会校验每个批次的 `batch_item_id` 数量、唯一性和完整性；缺失、重复或多出的 ID 会让执行失败，不会静默丢弃评论。
- 批量请求有独立缓存阶段，不会读取旧版单条缓存；原有 `quality`、`issue` 阶段保留。
- 如需回退，必须先从本人保留的、已验证可用的旧版工作流备份恢复；本仓库不包含旧版工作流。缓存代理保留旧单条阶段兼容能力。
- 这份测试版没有更改后续聚类/洞察逻辑，也没有承诺在未实测情况下必然达到 10 分钟。

## 8. 自动化测试

在**项目根目录**执行（离线测试，不访问 DeepSeek）：

```powershell
python -m pip install -r .\ai-cache-proxy\requirements.txt
python -m pip install pytest
Push-Location .\ai-cache-proxy
python -m pytest -q
Pop-Location
node .\evaluation\performance\test_batch_workflow.js
```

Python 测试覆盖旧阶段兼容、批量阶段 MISS/HIT、批量 ID 一一对应，以及缺失/重复 ID 不写入缓存。Node.js 测试会直接读取工作流 JSON，验证分批数量、HTTP 请求体格式和结果按评论 ID 正确展开。
